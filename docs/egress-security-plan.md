## 1. Задача и ожидаемый результат

Сделать локальный модуль, который перед передачей данных определённому
получателю обнаруживает поддерживаемые категории конфиденциальной информации
и применяет заданную приложением политику: разрешить или заблокировать передачу.

Основной сценарий преподавателя: локальная LLM предлагает вызов удалённого
инструмента, но в его аргументы вместе с полезными данными попадают персональные
данные или секреты доступа. Харнесс должен предотвратить запрещённую передачу.

В существующем проекте также используется внешний API LLM. Поэтому проверять
необходимо не только аргументы MCP-инструментов, но и контекст, отправляемый
провайдеру модели, включая запросы сжатия истории.

Результат первой версии:

- самостоятельный пакет детекции и принятия решений;
- явно включаемая защита в примерах с харнессом;
- проверка аргументов перед выполнением и запросов перед сетевой отправкой;
- безопасные сообщения о блокировках и журнал событий без содержимого запросов;
- воспроизводимая демонстрация без настоящих персональных данных и API-ключей;
- тесты детекторов, политики и фактического отсутствия запрещённой отправки.

Первая версия не изменяет полезную нагрузку автоматически. Очистка, маскирование
данных в рабочих запросах и замена значений псевдонимами — отдельное расширение
после проверки детекции и блокировки. Исключение — безопасное представление
диагностики: содержимое запросов не должно попадать в логи.

## 2. Границы задачи и модель угроз

### 2.1. Что защищаем

- Аргументы инструментов, предлагаемые моделью.
- Контекст внешней LLM: запрос пользователя, история, релевантные данные памяти,
  загруженные skills, результаты инструментов и сводка истории.
- Данные, которые могут повторно отправляться после HTTP-ошибки или потери
  MCP-сессии.
- Журналирование, диагностические сообщения и тексты ошибок, которые способны
  скопировать конфиденциальную информацию из запроса или ответа сервиса.

Источники утечки: ошибка модели, избыточные аргументы, промпт-инъекция через
пользовательский запрос или результат инструмента, отправка слишком широкого
контекста, небезопасная обработка ошибок.

### 2.2. Что считается получателем

Получатель определяется конфигурацией приложения и фактическим адресом клиента.
Модель и MCP-сервер не могут объявить себя доверенными через текст, название
инструмента, схему аргументов или `readOnlyHint`.

Политика различает как минимум внешний API LLM, MCP-сервис, явно объявленную
локальную операцию и локальный журнал событий. Ответ владельцу в локальном
терминале рассматривается отдельно от передачи стороннему сервису.

Локальная Go-функция может выполнять HTTP-запросы. Поэтому само слово
«локальный» и адрес из частной сети не являются достаточным основанием доверия.
Для встроенных инструментов назначение известно из кода; новые обработчики
должны явно описывать свои передачи и использовать защищённые клиенты.

### 2.3. Ограничения гарантий

Приложение, его конфигурация и подключённый код считаются доверенными.
Модуль не является песочницей: произвольный обработчик с собственным HTTP-клиентом
может обойти проверки приложения. Для защиты от недоверенного исполняемого кода
потребуются отдельная изоляция и ограничения сетевого доступа.

Гарантия относится к перечисленным точкам интеграции и поддерживаемым правилам
детекции. Отсутствие находок означает отсутствие совпадений с этими правилами,
а не доказательство публичности любого произвольного текста.

В первую версию не входят:

- обнаружение любых ФИО, адресов и коммерческих секретов по смыслу;
- полное распознавание произвольного шифрования, кодирования и скрытых каналов;
- анализ изображений, вложений, архивов и бинарных форматов;
- защита от сборки секрета из частей, переданных разными запросами;
- автоматическое определение законных оснований обработки персональных данных;
- сертификация и заявление соответствия нормативным требованиям;
- субагенты, AgentCard, A2A и замена существующего MCP на другой SDK.

## 3. Архитектурные обязательства

| Понятие | Обязательство реализации |
| --- | --- |
| LLM | Выбирает шаги и возвращает текст или `ToolCall`; не управляет политикой защиты. |
| Харнесс | Собирает контекст, управляет циклом и применяет ограничения выполнения и передачи. |
| Инструмент | Сохраняет имя, описание, схему и обработчик; не выполняет детекцию по выбору модели. |
| MCP-клиент | Получает каталог и отправляет разрешённые сообщения; не передаёт исполнение инструментов модели. |
| MCP-сервер | Продолжает самостоятельно выполнять полученные вызовы инструментов. |
| Транспорт | Доставляет сообщения; правила конфиденциальности не добавляются в `HTTPTransport`. |
| Память | Остаётся во внешнем хранилище; модуль не переписывает и не отправляет всё хранилище. |
| Контекст | Проверяется перед отправкой; роли, история, идентификаторы вызовов и результаты сохраняют структуру. |
| Системный промпт | Не изменяется защитным модулем от задачи к задаче. |
| Skill | Полный текст по-прежнему появляется после выбора модели через `load_skill`. |
| Шаг | Детекция не добавляет шаг; предложенный вызов учитывается по существующим правилам харнесса. |
| Лимиты | Время проверки учитывается в бюджете запроса; проверка поддерживает отмену. |

Модуль является используемым харнессом механизмом, а не инструментом из каталога
LLM, skill или агентом. Модель не может отказаться от его запуска.

Проверка запроса на валидность и безопасность один раз перед циклом сохраняется.
Контроль исходящих данных выполняется перед каждой соответствующей передачей;
это другая операция и другая точка жизненного цикла.

## 4. Пакеты, зависимости и минимальные контракты

### 4.1. Независимое ядро

Создать `internal/egress`. Пакет зависит только от стандартной библиотеки и не
импортирует `harness`, `llm`, `tools`, `mcp`, `memory` или `skills`.

Предварительные сущности:

| Сущность | Назначение |
| --- | --- |
| `Destination` | Доверенно заданный получатель: идентификатор, вид канала и конкретный адрес либо локальная операция. |
| `Attempt` | Планируемая передача: получатель, каноническая операция и типизированные фрагменты JSON-совместимых данных. |
| `Fragment` | Вид фрагмента, его семантическая область, структурный путь и соответствующий участок отправляемого сообщения. |
| `Finding` | Категория, идентификатор правила и внутренний путь к находке; без сохранения найденного значения. |
| `Detector` | Локальный анализ переданных данных с поддержкой `context.Context`. |
| `Policy` | Правила для сочетания получателя, операции и обнаруженных категорий. |
| `Decision` | `Allow` или `Deny`, безопасный код причины и ограниченный набор метаданных. |
| `Guard` | Единая точка оценки передачи, объединяющая детекторы и политику. |
| `ErrDenied` | Типизированный отказ для безопасной обработки вызывающим компонентом. |

Точные сигнатуры оформить перед первым кодовым этапом. Обязательные свойства:
оценка не изменяет вход, не выполняет HTTP-запросы и не включает секреты в ошибку.
Успешное решение и ошибка анализа различаются; ошибка не означает разрешение.

### 4.2. Направление зависимостей

```text
cmd / cli: сборка конфигурации и включение защиты
    ├── harness ────────────────┐
    ├── llm.Client ─────────────┤
    └── mcp.Client ─────────────┤
                               ▼
                         internal/egress
                               ▼
                    стандартная библиотека
```

Политика не реализуется отдельно в каждом клиенте. Клиенты вызывают один и тот
же переданный им `Guard` перед отправкой. Это программные API-клиенты, а не
нейросеть; их защитные проверки не меняют определение LLM.

### 4.3. Назначение инструмента

Сохранить контракт `tools.Toolbox`. Добавить в `tools.Tool` внутренние метаданные
назначения передачи, аналогично уже существующему `Dangerous`. Эти метаданные
не включать в `Tool.Spec()`, JSON Schema или сообщения модели.

- Встроенные локальные инструменты объявляют свои известные локальные операции.
- MCP-клиент назначает инструментам фактический адрес своего сервера, а не
  доверяет сведениям о доверии из ответа `tools/list`.
- При переподключении сохраняется проверка неизменности каталога.
- Неизвестное назначение в защищённом режиме приводит к безопасному отказу.
- Клиент дополнительно проверяет фактическую передачу, даже если метаданные
  инструмента или внешний вызывающий код оказались некорректны.

Не определять назначение разбором `Toolbox.Name()` или названия инструмента.

#### Встроенный `load_skill`

`load_skill` создаётся непосредственно в `Harness.New` и выполняется специальной
веткой `Harness.execute`, поэтому изменения только в `localtools` недостаточны.
При создании встроенного инструмента назначить ему внутреннее назначение
`harness_context` и каноническую операцию `tool_call/load_skill`.

Это назначение описывает локальную загрузку выбранного skill в контекст данного
харнесса. Оно не имеет сетевого адреса и не требует элемента в `h.route` или
дополнительного `Toolbox`. Его нельзя использовать для сетевого вызова или
вывести из строки имени произвольного инструмента.

В защищённой сборке с библиотекой skills явно проверить наличие правила для
этой внутренней операции. Отсутствие необходимого правила — ошибка настройки
при запуске, а не случайная блокировка всех skills при первом вызове. Пример
политики включает разрешение локальной загрузки из настроенной библиотеки.
Сохраняются проверки имени skill и существующий способ чтения через `Library`.

Разрешение локальной загрузки не разрешает передачу её содержимого наружу.
Полный текст появляется только после выбора модели, остаётся в контексте
этого харнесса и отдельно проверяется при отправке внешней LLM. При отказе
внешней передачи текст не удаляется и не переписывается ради обхода проверки.

### 4.4. Каноническая операция и пути находок

Политика оценивает смысл передачи независимо от её протокольной оболочки.
Зафиксировать следующий контракт до реализации детекторов и адаптеров:

- `Destination` — фактический настроенный получатель и канал передачи.
- `Operation` — пара «вид действия / имя»: например,
  `tool_call/search_messages`, `model_request/chat_completions` или
  `protocol_control/tools_list`.
- Протокольный метод, например `tools/call`, — отдельные метаданные адаптера.
  Он не заменяет имя инструмента в правиле разрешения его аргументов.
- `ArgumentPath` — структурный путь от корня аргументов семантического вызова.
  Внутреннее представление различает ключ объекта и индекс массива.
- `EnvelopePath` — отдельный внутренний путь от корня фактического сетевого
  сообщения. Он связывает проверенный фрагмент с отправляемыми данными.
- `FragmentKind` — вид фрагмента, назначенный доверенным адаптером по структуре
  API: значение данных, декларация схемы либо текст описания.

Пример одной и той же передачи:

| Точка проверки | Каноническая операция | Путь аргумента | Протокольная оболочка |
| --- | --- | --- | --- |
| `Harness.execute` | `tool_call/search_messages` | ключ `query` от корня args | Отсутствует. |
| MCP `Client.send` | `tool_call/search_messages` | ключ `query` от корня arguments | Метод `tools/call`, сетевой путь `params.arguments.query`. |

Для одинакового получателя и аргументов обе точки применяют одно правило и
получают одинаковое решение. Имена инструментов разбираются из фактической
структуры вызова, а не из свободного текста. У `tools/list`, `initialize` и
других служебных операций отдельные канонические имена и правила.

Разрешение поля — точное сопоставление канонического пути и операции.
Оговорённые правила массивов задаются явно. Не заменять совпадение пути
проверкой подстроки, последнего имени поля или неявным разрешением всего
`tools/call`. Экранированные ключи, точки и слеши в именах не должны изменять
систему координат или расширять разрешение.

Внешний запрос к LLM всегда имеет операцию `model_request/chat_completions`,
включая отправленные внутри него прошлые `ToolCall`. Упомянутый внутри контекста
инструмент не становится получателем этой передачи. Разрешение email для
`search_messages` на MCP-сервере не разрешает тот же email в контексте внешней LLM.

`Finding` хранит пути для внутреннего точного решения, но журнал получает
только безопасные метаданные. Недоверенные ключи и содержимое `EnvelopePath`
не включаются в пользовательскую причину или лог автоматически.

Общий код канонизации инструментальных аргументов находится в независимом
ядре и переиспользуется обеими точками; разбор оболочек API остаётся в адаптерах
соответствующих клиентов. Преобразование должно покрывать всё отправляемое
сообщение: неизвестные поля анализируются как данные, а не пропускаются.

## 5. Детекция первой версии

### 5.1. Поддерживаемые категории

1. Явно зарегистрированные приложением секреты: точное совпадение значения
   с локальной конфигурацией детектора. Не собирать всё окружение процесса и
   содержимое файлов с учётными данными. Пустые и слишком короткие значения
   отклонять как некорректную настройку этого детектора.
2. Поля с назначением секрета: согласованный список имён вроде `password`,
   `api_key`, `access_token`, `client_secret`, включая выбранные русские варианты.
   Непубличное значение такого поля не должно требовать известного префикса.
   Правило применяется к передаваемому значению, а не к объявлению параметра
   в JSON Schema; различение фрагментов описано в разделе 5.3.
3. Выбранные форматы токенов и блоков приватных ключей. Перечень форматов
   фиксируется в документации и тестах; он не объявляется исчерпывающим.
4. Email и заранее перечисленные форматы телефонов. Ограничения распознавания
   и ложные срабатывания документируются отдельно от секретов доступа.

Категория находки и разрешение передачи разделены: email может быть необходимым
параметром разрешённого поиска, но запрещённым дополнением к запросу погоды.
Нельзя запрещать все числа, адреса или непустые строки без учёта политики.

### 5.2. Обход полезной нагрузки

- Обрабатывать вложенные объекты, массивы, строки и имена полей.
- Анализировать весь отправляемый текст; не проверять только первые N символов.
- Установить пределы размера, глубины и числа элементов. Превышение приводит
  к отказу передачи, а не к отправке непроверенного остатка.
- Адаптер LLM раскрывает известные JSON-строки аргументов `ToolCall` для анализа:
  экранирование JSON не должно скрывать поле `password` от структурных правил.
- Поддержать нормализацию регистра имён полей и оговорённых разделителей,
  не меняя исходную полезную нагрузку.
- Не пытаться бесконечно декодировать произвольные строки. Поддерживаемые
  представления и предел вложенного разбора зафиксировать в тестах.
- Типы, которые невозможно безопасно разобрать, анализировать как ошибку,
  а не как отсутствие конфиденциальной информации.

Регулярные выражения и словари — детерминированная первая реализация.
Вызовы внешней LLM для классификации проверяемого секрета запрещены.

### 5.3. Схема инструмента и фактические данные

Один запрос к LLM содержит разные сущности: каталог с описаниями инструментов,
JSON Schema их параметров, тексты сообщений и реальные аргументы `ToolCall`.
Адаптер обязан различать их по известным позициям в структуре API.

| Фрагмент | Правило обработки |
| --- | --- |
| `parameters.properties.password.type = "string"` | Декларация поля, не значение пароля; само её наличие не запрещает передачу. |
| `parameters.properties.password.default` или элемент `examples` | Значение примера/по умолчанию; учитывать назначение соответствующего поля и проверять как данные. |
| `description`, `title` и другой текст схемы/инструмента | Проверять на известные секреты, поддерживаемые форматы токенов, ПДн и явно заданные текстовые присваивания. |
| Фактические `arguments.password` | Применять правило чувствительного поля независимо от наличия известного префикса. |
| JSON-строка в известном поле `ToolCall.function.arguments` | Разобрать ограниченно и проверить как фактические аргументы, сохранив связь с сетевым сообщением. |

Структурные имена свойств схемы и значения `type` не являются присваиванием
пароля. Однако сами строки, включая имена свойств, продолжают проходить
детекторы известных секретов и поддерживаемых форматов. Схемы не исключаются
из анализа целиком. Вложенные схемы обрабатываются по тем же правилам.

Маркировка фрагмента не принимается из текста модели или пользовательских
полей вроде `kind: "schema"`. Объект, похожий на схему внутри реальных
аргументов, сам по себе не получает исключение из правила секретных значений.
Нестандартные поля схемы анализируются как данные или текст по своей структуре.

При проверке фактического запроса адаптер использует те же виды фрагментов,
что и предварительная проверка. Повторный бесконтекстный обход всего JSON
не должен снова принять декларацию параметра за пароль. Сохраняется полное
покрытие строк; меняется применимость структурного правила, а не набор
отправляемых данных. Каталог, схемы и инструкции не переписываются.

## 6. Политика и включение защиты

### 6.1. Условия разрешения

Передача разрешается только если одновременно выполнены условия:

1. Получатель известен и разрешён конфигурацией.
2. Операция допустима для этого получателя.
3. Найденные категории разрешены для этой операции и, при необходимости,
   конкретных полей.
4. Анализ завершён без ошибки, превышения размеров или отмены.

Наличие `readOnlyHint: true`, отсутствие `Dangerous` и подтверждение пользователя
не отменяют запрет передачи. Для жёсткого отказа в первой версии не вводится
кнопка «всё равно отправить».

Неизвестные правила, ошибочная конфигурация, неопределённый адрес и ошибка
детектора приводят к отказу в защищённом режиме. Политика фиксируется при
запуске; модель не может менять её через запрос или инструмент.

### 6.2. Конфигурация

Предусмотреть JSON-файл политики с версией формата. Рекомендуемое включение:
`AGENT_EGRESS_POLICY=/путь/к/политике.json` для вариантов 02–04.

Оригинальные четыре учебных сценария сохраняются. Без явно указанной политики
они работают в прежнем режиме; запуск должен сообщать, что контроль исходящих
данных не включён. Если путь задан, любой сбой загрузки является ошибкой запуска:
автоматического перехода к режиму без защиты нет.

Вариант 01 остаётся примером без харнесса. Если ему передана настройка,
создающая ожидание защиты, запуск отклоняется с пояснением выбрать вариант
с харнессом. Он не должен создавать ложное впечатление защищённого режима.

В конфигурации нужны:

- версия формата;
- безопасные идентификаторы получателей и их фактические адреса;
- разрешённые операции и категории по назначению;
- при необходимости ограничения на поля конкретных инструментов;
- включённые детекторы и ограничения объёма обработки.

Секретные значения в пример политики не помещать. Не делать широкое исключение
для всего доверенного домена или всех данных: исключения должны быть связаны
с назначением, операцией и допустимым местом использования.

Загрузка и проверка политики, создание общего Guard и настройка клиентов
выполняются до первого сетевого запроса, в том числе до `mcp.Client.Connect`.
В защищённой сборке харнесс и все задействованные клиенты должны использовать
один экземпляр Guard с одной неизменяемой политикой. Несогласованный режим,
неподключённый Guard у клиента и отсутствие обязательного локального правила
`load_skill` выявляются при сборке приложения, без перехода к работе без защиты.

### 6.3. Адреса и авторизация

Сравнивать разобранные URL по схеме, хосту, порту и оговорённому пути API,
а не через `strings.Contains`. Для внешней передачи использовать HTTPS.
HTTP допускается в явно настроенных локальных демонстрациях и тестах.

URL с учётными данными и секретными параметрами не использовать. В защищённом
режиме запретить автоматическое следование редиректам в подключённых клиентах,
чтобы разрешение одного адреса не разрешало отправку на другой.

API-ключ провайдера передаётся штатным механизмом авторизации только своему
настроенному получателю. Разрешение заголовка авторизации не разрешает отправку
этого ключа в теле запроса, аргументах инструмента или логах.

Разрешение операции в модуле не подменяет сетевую политику платформы,
а доступность домена по сети не подменяет разрешение конфиденциальных данных.

## 7. Точки интеграции и поведение цикла

### 7.1. Харнесс: вызов инструмента

В `Harness.execute` сохранить следующий порядок:

```text
проверить существование инструмента
→ разобрать JSON и проверить схему
→ определить назначение из доверенных метаданных
→ проверить передачу модулем egress
→ при отказе вернуть безопасный результат ошибки
→ для load_skill выполнить внутреннюю загрузку в контекст и вернуть результат
→ при разрешении применить существующее подтверждение Dangerous
→ выполнить локальный вызов или обратиться к MCP-клиенту
→ записать результат инструмента в контекст
```

Ветка `load_skill` использует назначение и правило из раздела 4.3; к поиску
`h.route` для неё не переходить. Проверка локальных аргументов этой операции
не подменяет проверку полного загруженного текста при отправке контекста LLM.

Не записывать исходные аргументы в лог до проверки. Не выводить их целиком
в вопросе подтверждения. Использовать имя операции и разрешённое безопасное
представление необходимых для подтверждения параметров.

Заблокированный вызов получает ровно один результат с исходным `ToolCallID`.
В пакетном ответе модели каждому вызову соответствует свой результат, включая
отклонённые и пропущенные. Операция не считается успешно выполненной.

Повторная попытка модели снова проходит проверку. Блокировка не обнуляет
счётчик шагов и не создаёт отдельного вызова LLM вне общего цикла.

### 7.2. LLM-клиент: фактическая отправка контекста

В общей ветке `Client.complete` после формирования тела и перед HTTP-отправкой
вызывать проверку для фактического адреса провайдера. Это покрывает `Complete`,
`CompleteAnswer` и вызов сжатия истории из `manageContext`.

Адаптер передаёт детектору весь контекст и описания инструментов, включая
известные вложенные JSON-строки, с видами фрагментов из раздела 5.3. Операция
остаётся внешним запросом к LLM; разрешения для вложенных упоминаний
MCP-инструментов на неё не переносятся.

Адаптер строит проверяемое представление из окончательно сформированного тела
либо доказывает его структурную эквивалентность этому телу. Отправляемое тело
после проверки неизменяемо; дополнительная сборка не должна добавлять
непроверенное пользовательское содержимое или менять классификацию фрагментов.

При отказе перед отправкой не производится ни одной HTTP-попытки. Возвращается
типизированная безопасная ошибка. Харнесс прекращает этот запрос пользователю,
не пытаясь отправить тот же запрещённый контекст модели для объяснения отказа.

При сетевых повторах проверенные данные остаются неизменными; новая полезная
нагрузка или другой адрес требуют новой проверки. Нельзя изменять исходный
контекст для обхода отказа, удалять историю или подменять системный промпт.

### 7.3. MCP-клиент: фактическая отправка аргументов

Проверять исходящие динамические параметры в общем пути `Client.send` до
`Transport.Send`. Главная операция — `tools/call`, но курсоры и другие
динамические параметры также не должны обходить проверку.

Для `tools/call` адаптер восстанавливает из `params` имя инструмента и корень
аргументов, формируя ту же каноническую операцию и пути, что и харнесс
(раздел 4.4). Оболочка JSON-RPC сохраняется неизменной. Неизвестные и лишние
поля не игнорируются: они анализируются отдельно без расширения точного
разрешения для известного аргумента.

Служебные сообщения `initialize` и `notifications/initialized` имеют явно
оговорённую минимальную структуру без пользовательского контекста. Пути
отправки уведомлений перечислить при реализации, чтобы у них не возник
отдельный непроверяемый канал произвольных данных.

Проверка выполняется и при прямом обращении к защищённому MCP-клиенту,
минуя `Harness.execute`. Переподключение не отменяет политику и не меняет
доверие к назначению. Повторный `tools/call` проходит тот же общий путь.

`HTTPTransport` сохраняет доставку, JSON/SSE и управление сессией.
Детекторы и правила конфиденциальности туда не добавляются.

### 7.4. Время, отмена и неизменность данных

Проверки в харнессе получают контекст с оставшимся бюджетом времени.
Ожидание подтверждения по-прежнему исключается из бюджета: нельзя создавать
один таймаут до подтверждения и случайно включать в него ожидание пользователя.
После подтверждения оставшееся время пересчитывается для выполнения.

Оценка не изменяет исходные map, срезы и структуры сообщений. Конфигурация
детекторов неизменяема после запуска. Поддержать конкурентные обращения без
гонок и общего буфера, содержащего данные нескольких запросов.

Прежняя проблема точности ограничения токенов не должна скрываться за новым
модулем: эта работа не заявляет строгую верхнюю границу расходов на API.

## 8. Журналы, ошибки и вывод пользователю

В защищённом режиме использовать журнал событий, содержащий только безопасные
метаданные: канал, настроенный идентификатор получателя, идентификатор правила,
категорию, решение и количество находок.

Не включать:

- найденные значения, исходные запросы, полный контекст и результаты;
- полный URL, заголовки авторизации и тексты секретной конфигурации;
- неконтролируемые сообщения ошибок удалённого сервиса;
- имена полей или пути, если они сами содержат пользовательские данные;
- хеши низкоэнтропийных персональных данных как замену безопасной диагностике.

Проверить текущие места вывода: аргументы и результаты в `harness.Run`, память
при сборке контекста и записи фактов, подтверждения `Confirm`, ошибки LLM/MCP,
`Fatal`, а также аргументы вызова в `mcp.Server`.

Отключить вывод содержимого на стороне учебного MCP-сервера для демонстрации
защиты; остановка передачи клиентом не должна быть единственной защитой логов.
Нельзя гарантировать журналирование стороннего сервера, которым проект
не управляет.

Локальный терминал владельца и внешний получатель — разные назначения.
Полезные данные, разрешённые владельцу, не должны автоматически запрещаться
для показа ему только потому, что их нельзя послать стороннему сервису.
При этом сообщение об отказе не повторяет обнаруженный секрет.

## 11. Матрица обязательных проверок

| --- | --- |

| Тот же email в другом поле или инструменте, включая ключи с точкой/слешем | Отказ без широкого исключения для tools/call и без обхода через путь. |

| Чувствительное поле во вложенном объекте или массиве | Находка обнаружена на любой поддерживаемой глубине. |
| Секрет в JSON-строке аргументов `ToolCall` внутри контекста LLM | Передача контекста заблокирована. |

| Отсутствует правило load_skill при включённой библиотеке skills | Явная ошибка настройки при запуске, а не случайный отказ неизвестного назначения. |
| Прямой вызов защищённого `mcp.Client` | Проверка действует без `Harness.execute`. |

| Опасный инструмент и отказ egress | Подтверждение не запускает запрещённую передачу. |

| Подмена метаданных доверия в каталоге MCP | Применяется фактический настроенный получатель. |
| Неизвестный адрес, операция или назначение | Безопасный отказ защищённого режима. |
| Редирект с разрешённого адреса | Нет автоматической отправки на новый адрес. |
| Авторизация своим API-ключом | Ключ используется штатно только для настроенного получателя. |
| Тот же ключ в теле запроса или аргументах | Отказ независимо от разрешённой авторизации. |
| Ошибка детектора, превышение объёма или отмена | Запрос не отправлен; нет молчаливого отключения защиты. |
| Изменение входных данных или конфигурации оценкой | Тест падает; такое изменение запрещено контрактом. |
| Одновременные проверки | Нет гонок и смешивания данных запросов. |
| Локальный вывод владельцу | Применяется отдельная политика, не запрет для внешнего сервиса. |
| Режим без политики | Сохранён прежний учебный сценарий с явным указанием отсутствия защиты. |
| Неправильная политика при включённой защите | Ошибка запуска; перехода в незащищённый режим нет. |
| Клиент без Guard или с другой политикой в защищённой сборке | Ошибка сборки приложения; сетевой вызов таким клиентом не выполняется. |
| Проверка запроса и проверка окончательного сериализованного тела | Полное покрытие данных и согласованные решения при сохранении видов фрагментов. |

Использовать `httptest` и счётчики запросов/обработчиков. Блокировка подтверждается
не только текстом ответа, но и отсутствием сетевого вызова или исполнения.
Проверять захваченные логи, stderr, ошибки и безопасные уведомления на отсутствие
синтетических секретов. Набор ожидаемых решений фиксируется до реализации правил.

Для оценки отдельно приводить число корректных обнаружений, пропусков, ложных
срабатываний и корректных разрешений по категориям. Не подбирать набор только
под уже реализованные выражения и не объявлять точность на нём общей гарантией.

## 12. Демонстрация преподавателю

Одна команда запускает локальный тестовый получатель и заранее заданные
передачи. В конфигурации этот получатель явно считается внешним по уровню
доверия, хотя физически работает на localhost.

Примеры:

1. `get_weather` получает только город: запрос доходит до получателя.
2. В текст добавлен искусственный секрет `DEMO_ONLY_SECRET_001`, зарегистрированный
   исключительно для демонстрации: запрос блокируется, получатель ничего не видит.
3. Email `user@example.invalid` передаётся в разрешённый параметр поиска одному
   сервису и запрещается в несвязанном запросе другому.
4. Те же конфиденциальные данные появляются в контексте внешней LLM:
   срабатывает отдельная точка контроля отправки контекста.

Вывод: номер сценария, решение, безопасный код причины, число полученных запросов.
Затем показать, что LLM, харнесс, инструменты, клиенты и транспорт сохранили
свои роли. Для детерминированного прогона используется заглушка модели,
аналогичная уже существующим тестам, а не новый агент-классификатор.
