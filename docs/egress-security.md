# Контроль исходящих данных

Модуль `internal/egress` выполняет локальную проверку перед передачей данных.
LLM выбирает шаг; харнесс проверяет допустимость вызова; MCP-сервер выполняет
разрешённый удалённый инструмент. Проверка не является инструментом модели,
skill или отдельным агентом. Внешняя LLM для детекции не используется.

## Быстрая демонстрация

Из корня репозитория, без API-ключа и внешних сервисов:

```bash
go run ./cmd/egress_demo
```

Шесть сценариев проверяют разрешённый вызов, блокировку искусственного секрета,
разрешение email только для нужного поля поиска, запрет того же email в запросе
погоды, защиту контекста LLM и допустимость декларации `password` в схеме.
Программа завершается с ненулевым кодом при нарушении ожидаемого поведения.
Тестовые получатели находятся на localhost, но имеют отдельные назначения
политики. Адрес localhost сам по себе не присваивает доверие.

## Включение для примеров 02–04

Сначала настройте `LLM_BASE_URL`, `LLM_MODEL` и `LLM_API_KEY`, как в README.
Пример политики рассчитан на OpenRouter и учебный MCP-сервер по адресу
`http://127.0.0.1:8000/mcp`.

```bash
export AGENT_EGRESS_POLICY=config/egress.example.json
go run ./cmd/03_harness_local_tools "Какая погода в Казани?"
```

PowerShell:

```powershell
$env:AGENT_EGRESS_POLICY="config/egress.example.json"
go run ./cmd/03_harness_local_tools "Какая погода в Казани?"
```

Для варианта 04 в отдельном терминале запустите `go run ./cmd/mcp_mail_server`,
затем в терминале с переменными — `go run ./cmd/04_harness_mcp_tools`.
Политика загружается до `Connect`. Неизвестный адрес, отсутствующая операция,
неверный файл и частично подключённая защита отклоняются.

Без `AGENT_EGRESS_POLICY` примеры работают в прежнем учебном режиме и явно
сообщают, что контроль исходящих данных выключен. Вариант 01 остаётся примером
без харнесса и отклоняет запуск с этой переменной, чтобы не обещать защиту.

## Какие данные обнаруживаются

- Значения из явно указанных в `secret_env` переменных; отсутствующее или
  слишком короткое значение делает настройку некорректной.
- Значения полей `password`, `api_key`, `access_token`, `refresh_token`,
  `client_secret`, выбранных русских эквивалентов и текстовые присваивания.
- Поддерживаемые префиксы токенов OpenAI/OpenRouter/GitHub и заголовки PEM
  приватных ключей. Это конечный набор форматов, а не все существующие секреты.
- Email и телефоны выбранных форматов: 11 цифр с 7/8, включая формат +7,
  а также международный учебный диапазон +1 ... 555-01xx.

CLI автоматически регистрирует `LLM_API_KEY` в общем неизменяемом Guard.
Этот ключ не может уйти через MCP, рабочий JSON или `OpenAI-Project`, даже если
его префикс неизвестен. Клиент модели дополнительно проверяет свой APIKey
при прямом использовании. Штатный `Authorization: Bearer ...` направляется
только настроенному провайдеру. Автоматические HTTP-редиректы в защищённых
клиентах выключены.

Проверяются также ключи объектов, массивы и JSON-числа. Сохраняются исходная
лексема и точная десятичная нормализация: экспонента и округление float64
не должны скрывать числовой секрет. В защищённом режиме числовые аргументы
пользовательского обработчика имеют тип `json.Number`; валидатор инструментов
принимает его и обычный `float64`.

## Точные разрешения политики

Формат — JSON, версия 1. Неизвестные поля и повторяющиеся ключи запрещены.
В `targets` задаются безопасный `id`, фактический `destination` и `rules`.
Разрешение категории имеет точный путь от корня семантических аргументов:

```json
{
  "operation": {"kind": "tool_call", "name": "search_messages"},
  "allow": [{"category": "email", "path": ["query"]}]
}
```

Это разрешает email в `query` указанного инструмента у указанного получателя.
Разрешение не переносится на соседнее поле, другой инструмент, оболочку
`tools/call` или контекст внешней LLM. Строка пути обозначает ключ объекта,
целое число — индекс массива. Неявных wildcard и совпадений по суффиксу нет.
Категории исключений: `email`, `phone`, `secret`. Зарегистрированные credentials
не имеют исключения для передачи в полезной нагрузке.

Назначения `local` и `internal` не имеют HTTP-адреса. `load_skill` использует
`internal/harness_context` и операцию `tool_call/load_skill`. Отсутствие правила
при включённых skills останавливает запуск. Разрешение загрузки skill не
разрешает отправку его текста наружу.

Для провайдера и серверов указывайте точный URL: для модели — с окончанием
`/chat/completions`, для MCP — адрес endpoint. URL с учётными данными,
query-параметрами или fragment не принимаются. Внешние адреса требуют HTTPS;
HTTP поддерживается только для явно внесённого loopback IP. Разрешение сети
в среде и разрешение данных в политике — отдельные проверки.

## Схемы, блокировка и журнал

`properties.password.type = "string"` — декларация параметра. Она не является
паролем. Однако `description`, `default`, `examples` и строки во вложенных
схемах проверяются. Метку схемы назначает адаптер по позиции в API;
пользовательское поле `kind: "schema"` не создаёт исключение.

При блокировке инструмент не исполняется и получает безопасный результат
с исходным `ToolCallID`. При запрете отправки внешней LLM запрос завершается
ошибкой до HTTP. Аргументы, память, системный промпт и загруженные skills
автоматически не переписываются. Блокировка не добавляет нового шага агента.

В защищённом режиме подробные логи харнесса заменены уведомлениями без
содержимого. Журнал Guard содержит только настроенный идентификатор получателя,
код решения и число находок. Недоверенные ошибки не копируются в диагностику.
Учебный MCP-сервер не выводит аргументы и идентификаторы сессий.

Примерная политика разрешает email в поиске учебного MCP, но не в контексте
OpenRouter. Поэтому полученное письмо или релевантная память с email остановят
последующую отправку внешней LLM. Это ожидаемое решение данной политики;
разрешения меняются явно для выбранного назначения и точного поля.

## Ограничения

Правила не распознают все ФИО, адреса, смысловые тайны, обфускацию, изображения,
архивы и скрытые каналы. Возможны пропуски и ложные срабатывания. Обычный текст
не разбирается бесконечно как вложенные JSON/кодировки; известные JSON-строки
аргументов ToolCall разбираются адаптером.

Проверяемый JSON ограничен размером, глубиной и числом узлов. У чисел есть
дополнительные границы длины и экспоненты, у реестра секретов — границы размера.
Превышение и ошибки анализа приводят к отказу, а не к отправке остатка.
Проверка не гарантирует общую память процесса или жёсткий лимит стоимости API.

Код и конфигурация считаются доверенными. Произвольный обработчик со своим
HTTP-клиентом способен обойти механизм; модуль не является системной песочницей.
При добавлении сетевых инструментов используйте защищённый клиент и явно
объявляйте назначение. Реальный внешний сервис может вести собственные логи;
этот репозиторий ими не управляет.

## Проверки

```bash
go build ./...
go vet ./...
go test -race -count=1 ./...
go run ./cmd/egress_demo
```

Тесты проверяют фактическое число сетевых запросов, обработчиков и обращений
к модели, а также прямой MCP-вызов, переподключение, редиректы, ошибки,
загрузку skills, память, сжатие истории, неизменность данных и журналирование.
Все секреты тестов искусственные; проверка реального API-ключа не требуется.

Согласованное проектирование сохранено в [плане](egress-security-plan.md)
и [ревью плана](egress-security-plan-review.md). Эти документы фиксируют
предшествовавший реализации этап.
